# Этап 2: состояние и хранение

## Границы

Только этап 2: неизменяемые модели, JSON DataStore, Flow/StateFlow, редьюсеры,
миграция трёх SharedPreferences-хранилищ и удаление use case-обёрток.
Сохранить Fragment/XML, навигацию, лимит десять и правила пересчёта.
Не выполнять этап 3 (api/impl, mediators), Compose, обновление всех библиотек,
переработку камеры/permissions и снятие зависимости подкрепления от камеры.

## Контракты

- TokensRepository: поток полного поля, suspend-операции отметки по стабильному ID,
  количества, цвета и очистки. Количество и отметки меняются одной транзакцией.
- EffectsRepository: поток настроек и suspend-установка флагов.
- ReinforcementRepository в существующем общем data-модуле: поток настройки показа
  и URI, suspend-запись. Без дополнительных делегирующих repository/storage-слоёв.
- Сохраняемые DTO внутренние. У каждого экрана собственная ViewModel и UiState.
  Чистые редьюсеры не выполняют I/O или эффекты. Нет отдельного UiCache.
- Победа только по результату успешной пользовательской отметки, не при подписке,
  восстановлении, изменении размера или возвращении на экран.

## Хранение

Три JSON DataStore, по одному экземпляру на файл. Миграция до первого состояния:
TokensPreferences (точные позиции приоритетнее старого счётчика),
WinEffectsPreferences, ReinforcementPreferences (сырой флаг, не доступность камеры).
ID сохраняются. Версия формата и маркер миграции защищают от повторного импорта.
Legacy-файлы остаются, но рабочие записи прекращаются. Повреждение/ошибка чтения
не заменяются пустым прогрессом. Ошибка записи не считается успехом.

4. Реактивные настройки эффектов; сохранение поведения победы.
5. Транзакционное поле; все потребители; атомарные клики, без ручного refresh.

7. Очистка DI/обёрток, документация, полный JVM-прогон, debug APK и эмулятор.

   Не совмещать механический перенос с Compose, обновлением всех зависимостей

5. После каждой фичи — тесты, debug-компиляция, проверка навигации и отдельный
   стабильный коммит. Перед реализацией уточнить конечные имена модулей.

## Критерии результата

Сохранены правила переноса отметок, все настройки и URI. Поздний подписчик и две
ViewModel получают согласованное поле. Быстрые клики/resize не теряют записи.
Перезапуск не повторяет импорт или фанфару. Ошибки видимы, диалог закрывается только
после записи. Числовые значения вынесены в константы, включая повторяемые в тестах.

## Согласованное решение для этапа Compose: выбор цвета

- При переносе диалога цвета использовать [colorpicker-compose от skydoves](https://github.com/skydoves/colorpicker-compose), зависимость `com.github.skydoves:colorpicker-compose`.
- Заменить текущие ColorPickerView/ColorPickerDialog на `HsvColorPicker` внутри Compose-диалога. Версию подобрать при реализации под используемые Kotlin и Compose и зафиксировать в version catalog.
- Сохранить существующие ViewModel и DataStore-контракт: передавать сохранённый цвет как начальный, записывать выбранный цвет по подтверждению, закрывать диалог после успешной записи и показывать ошибку с возможностью повтора. Отмена не меняет сохранённый цвет.
- После переноса всех потребителей удалить старую зависимость `com.github.skydoves:colorpickerview`. Реализация относится к этапу Compose; текущая запись фиксирует выбор библиотеки в плане.
